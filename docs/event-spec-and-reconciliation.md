# Event specification and CRM reconciliation — skyliftgroup.com

Date: 2026-10-08 · GA4 property `555951601` · stream `G-L6KM3R8YGF`

---

## 1. The callback situation, stated honestly

**There is no official LeadConnector documentation for the postMessage events
the embedded form and calendar emit.** Everything public is third-party
write-ups and pull requests. They agree on the message *names* and **disagree on
the origin**, and one reported payload shape conflicts with the others.
LeadConnector's own help article states its external tracking script does not
support iframe-embedded forms, so a postMessage listener is the only route.

What the sources describe:

| Signal | Reported shape | Agreement |
|---|---|---|
| Inquiry accepted | array, `[0] === "set-sticky-contacts"`, then a key, contact JSON, locationId, fingerprint | One PR; a second source could not be confirmed |
| Booking completed | array, `[0] === "msgsndr-booking-complete"`, `[1]` carries `calendarId` | Two sources agree on the name |
| Either, alternative | object with `type: "form"` / `"appointment"` | One guide, conflicts with the array shape |
| Origin | `api.leadconnectorhq.com`, `leadconnectorhq.com`, `msgsndr.com`, `gohighlevel.com` | **Sources disagree** |

**Therefore the implemented signatures are plausible but UNVERIFIED against this
account.** They have not been observed on a real submission. The failure mode is
deliberate: a strict matcher that does not match fires nothing — silence, never
a false conversion.

Two further facts that shaped the build:

- The reported inquiry payload **carries contact JSON including email, full name
  and phone**. Nothing from any payload body is read into an event.
- The reported booking payload **has `fingerprint` and `calendarId` but no email
  or contactId**, so it cannot be matched to a contact on its own. That is why
  reconciliation needs our own identifier (§4).

## 2. Event specification

### Conversions — fired only on a confirmation message from an allow-listed origin

| Event | Fires when | Parameters |
|---|---|---|
| `generate_lead` | The embed reports an inquiry was accepted | `lead_ref`, `page_path`, `source: "ghl_form"` |
| `booking_complete` | The embed reports an appointment was booked | `lead_ref`, `page_path`, `source: "ghl_calendar"`, `calendar_id` when present |

`calendar_id` identifies a calendar, not a person. Every other parameter is
generated by us. **No payload content is ever forwarded.**

### Intent — never conversions, never key events

| Event | Fires when |
|---|---|
| `book_call_click` | A "Book a Free Strategy Call" link is clicked |
| `phone_click` | A `tel:` link is clicked |
| `email_click` | A `mailto:` link is clicked |
| `page_view` | One per route — initial load, client navigation, back/forward |

A click is not a lead. Marking any of these a key event would report intent as
outcome; `book_call_click` may be marked key for reporting convenience, but its
count is clicks, not booked calls.

Not implemented: a `chat_open` event. The chat widget's open signal is not
documented and has not been observed, and guessing it would be inventing a
callback.

### Naming note

`form_submit` is deliberately **not** used for conversions. GA4 enhanced
measurement has `formInteractionsEnabled: true` and emits its own `form_submit`,
so reusing the name would merge two different things.

## 3. Counting rules

**De-duplication is not session-wide.** A visitor who inquires, books, then
sends a second genuine inquiry an hour later is three real events and is counted
as three. Only the same message arriving twice within 5 seconds collapses — a
transport artefact, not a second prospect. Verified by test: a repeat inside the
window counts once; the same event after the window counts again; a different
conversion kind is never suppressed by another kind's de-duplication.

**One prospect who both inquires and books is one qualified lead, not two.**
`generate_lead` and `booking_complete` are separate events by design, because
they are different actions worth measuring separately. The reporting rule is:

> Qualified leads = **distinct `lead_ref`** with at least one conversion event.
> Never the sum of `generate_lead` + `booking_complete`.

## 4. CRM reconciliation

### The identifier

`lead_ref` — generated in the browser, stored in `localStorage`, format
`slg-` + 16 hex characters. Random. It is **not** derived from anything about
the visitor, contains no personal data, and is safe in GA4.

### How to join GA4 to LeadConnector

The booking payload carries `fingerprint` and `calendarId` but no contact
identifier, so the embed alone cannot join a GA4 event to a CRM record. The join
has to be carried in.

**Proposed method — requires one verification before it can be relied on:**

1. Add a hidden custom field on the LeadConnector form, e.g. `lead_ref`.
2. Pass the value into the embed as a URL parameter on the iframe `src`.
3. LeadConnector stores it on the contact; GA4 has it on the event; the two join
   on an identifier that is meaningless outside this pairing.

**Unverified step:** whether LeadConnector prefills a custom field from a URL
parameter *on an embedded iframe form* has not been confirmed on this account.
Third-party guides describe URL-parameter prefill for GHL forms, but that is not
the same as confirming it for this embed. It needs one check inside
LeadConnector before being built.

Until then GA4 reports conversion **counts** that cannot be tied to named CRM
records — which is the correct limitation to state rather than work around.

### What must never be done

Passing name, email or phone into GA4 to make the join easier. It breaches
Google's policy on personal data and is unnecessary — a random reference does
the same job.

## 5. Confirming the real payload

Everything in §1 is resolved by one real submission.

1. On the live site, in the browser console:
   `localStorage.setItem('slg-embed-debug','1')` then reload.
2. Submit the inquiry form, or complete a booking.
3. The console logs `[slg conversion probe]` with the true origin and payload.
   `[iFrameSizer]` lines are resize chatter and are ignored.
4. Send that output and the matcher gets tightened to the observed shape.

The probe is inert unless that flag is set, logs locally only, and sends nothing
anywhere.

**No real test submission has been made.** A live test creates a real contact and
may trigger real notifications, so it needs specific permission.
